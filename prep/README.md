## How to use this

**Two days before:** read `INTERVIEW_PREP.md` end to end once. Then read the five concept files —
they exist so that when someone asks a follow-up one level deeper than your prepared answer, you have
somewhere to go.

**The night before:** re-read sections 5 and 6 of the main doc (weak spots and Q&As), plus the
cheat-sheet table at the bottom. Those are the highest-yield pages.

**Ten minutes before:** the cheat sheet and the "numbers to have ready" line.

**The core tactic:** every concept file ends with a checklist. If you can tick every box, you can
hold a conversation about this project rather than recite one.

## The three things that make this project interview-worthy

1. **A real trust boundary, enforced by code ordering.** Redaction happens before every egress point
   in `pipeline.py`, and you can verify that property by reading one file. That's a security *design*,
   not a security *feature*.

2. **Deterministic tokenization is what makes the whole thing work.** The read-before-write at
   `vault.py:75` is four lines and the entire system depends on it — without it, retrieval and
   unmasking both collapse. Being able to explain *why* is the difference between having built this
   and having followed a tutorial.

3. **The known flaws are as valuable as the working parts.** Section 5 of the main doc documents 15
   genuine problems — an unauthenticated PII endpoint, no tenant isolation, a dead config file, an
   overlap algorithm that contradicts its own docstring, a retry decorator that catches the wrong
   exception, a regex pattern scored below its own threshold. Naming these before an interviewer finds
   them demonstrates engineering judgement far better than a clean-looking project with hidden
   problems.
